# How Much I Get From Codex

**[English](README.md) · [中文](README.zh-CN.md)**

> 一个油猴脚本，算出 OpenAI 从来不告诉你的那个数字：**你的 Codex 订阅到底值多少钱的 API 用量。**

OpenAI 从没公布过「什么订阅能用多少额度」。分析页只肯给你一根进度条 ——
*Monthly usage limit，还剩 70%* —— 分母从来没出现过。剩下 70% 的**什么**？

这个脚本把分母算出来。

## 它回答什么

- 本周期的额度上限大概是多少钱
- 已经花了多少、还剩多少、按当前速度什么时候用完
- 到订阅续费之前，还能拿到多少额度
- **这一笔订阅费实际买到了几份额度。** 窗口按自己的时钟重置，所以一个账期里常常不止一份 ——
  烧完一份、等到重置，续费之前又开出完整的一份
- 一个 turn 花你多少钱，一千行代码花你多少钱
- 哪一天、哪个模型、哪个入口、哪个技能最烧钱

**不点开就不发任何请求。** 页面加载时不发，后台不轮询，关掉之后也不留东西在跑。

## 原理

接口把两半信息分别放在两个地方，谁也不挨着谁：

| 接口 | 给了什么 | 缺了什么 |
|---|---|---|
| `/backend-api/wham/usage` | 本周期**已用百分比** | 分母 |
| `/backend-api/wham/usage/daily-workspace-user-token-usage-breakdown` | 每天每模型的 **token 明细** | 金额 |

拼起来：

```
每模型 token × 官方 rate card = 消耗的 credits   精确
credits ÷ 已用百分比           = 额度上限        推算
credits × $0.04               = 美元
```

### 为什么说 credits 这一步是精确、不是估算

因为验过。`/backend-api/wham/usage/daily-token-usage-breakdown` 会返回 OpenAI 自己算的
各模型占比。拿 2026-07-22 那天比对：

| 模型 | OpenAI 自己给的 | 本脚本用 rate card 独立算的 |
|---|---|---|
| gpt-5.6-sol | 99.70738778824162 % | 99.7074 % |
| gpt-5.4 | 0.17148759273530126 % | 0.17148 % |
| gpt-5.4-mini | 0.12112461902308662 % | 0.12117 % |

吻合到 4~5 位有效数字。rate card 不是对 OpenAI 计价函数的近似，**它就是那个计价函数**。

整条链路上唯一的推算，是最后那一次除法，加上 credits 换美元的汇率。
界面全程把这个区别摆在明面上：**实线蓝 = 实测，虚线琥珀 = 推算。**

### 往后推的逻辑

额度窗口和账期是两个互不相干的时钟。窗口从自己的重置点往前滚，所以一个账期里
装的窗口个数往往不是整数。

**往后数是硬的** —— 窗口长度固定，从 `reset_at` 起，到续费日之间的每一条边界都算得准。
**往回数不硬** —— 中途要是发生过提前重置，前面每一条边界都会移位。所以过去的周期会标明
「边界近似」，而且**绝不参与平均**。

一旦有了完整跑完的周期，**只用最近的那一个**来推后面的速度。把老周期一起平均，
恰好会把你想看的那个变化抹平。而且一个过去的周期只有在**它的每一天都取到了数**的前提下才算数 ——
拿一段残缺的数据当整个周期用，会让所有基于它的推算都偏低。

**发放**和**用得掉**是两回事。**窗口一开就是满额发放**，哪怕账期只剩两天；这时候限制你的是时间，
不是额度。所以「还能拿到」按开出的份数足额算，另有一行单独说明：按上一个完整周期的用法，
你实际能用掉其中多少。

### 什么时候它拒绝猜

窗口长度是从接口读的，绝不假设 —— 同样的套餐，有的账号是周窗口，有的是月窗口，还有的跑 5 小时窗口。

**窗口不到一天时，脚本拒绝推算任何东西，并且说明原因。** 用量只按整个 UTC 天上报，
拿一整天的花费去除一个五小时窗口的百分比，会算出好几倍大的额度。空着比给一个笃定的错数好。

同理，fast mode 只在 OpenAI 公布了倍率的模型上计价。跑了 fast 但没有公布倍率的模型按标准价计，
并明确标注"实际更高"，而不是把邻近模型的倍率安到它头上。

### Rate card

credits / 1M tokens，来自[官方 rate card](https://help.openai.com/en/articles/20001106-codex-rate-card)：

| 模型 | 未缓存输入 | 缓存输入 | 输出 |
|---|---|---|---|
| gpt-5.6-sol | 125 | 12.5 | 750 |
| gpt-5.6-terra | 62.5 | 6.25 | 375 |
| gpt-5.6-luna | 25 | 2.5 | 150 |
| gpt-5.5 | 125 | 12.5 | 750 |
| gpt-5.5-cyber | 500 | 50 | 3000 |
| gpt-5.4 | 62.5 | 6.25 | 375 |
| gpt-5.4-mini | 18.75 | 1.875 | 113 |
| gpt-5.3-codex | 43.75 | 4.375 | 350 |
| gpt-5.2 | 43.75 | 4.375 | 350 |

Fast mode 另算倍率：GPT-5.6 / 5.5 是 **2.5×**，GPT-5.4 是 **2×**
（[来源](https://learn.chatgpt.com/docs/agent-configuration/speed)）。脚本读 `speed` 字段，两档分开计价。

## 安装

这个仓库是私有的，平时那种一键 raw 链接打不开，手动装：

1. 装 [Tampermonkey](https://www.tampermonkey.net/)
2. 打开 Tampermonkey 面板，新建脚本，把
   [`how-much-i-get-from-codex.user.js`](how-much-i-get-from-codex.user.js) 的内容粘进去
3. 打开 <https://chatgpt.com/codex/cloud/settings/analytics>，点角落里那个标签

以后如果把仓库转成公开，raw 链接就能一键安装，Tampermonkey 也会顺着 `@updateURL` 自动更新。

界面语言跟随浏览器，也可以在面板里切。

## 已知的偏差，以及各自的方向

这些都不是未知数，是**方向已知**的偏差。看数字的时候心里有数就行。

| 来源 | 方向 |
|---|---|
| **credits 换美元**按 1 credit = $0.04（1000 credits = $40）。OpenAI 从没公布过这个汇率，此值来自额度购买页 | 汇率不对的话，所有金额等比例偏移。改脚本顶部的 `USD_PER_CREDIT` |
| **周期边界和天对不齐。** 窗口按精确时间戳开始，但用量只能按整个 UTC 天取，而且接口拒绝 `group_by=hour` | 首日会多算，所以**花费偏高、推算额度也偏高**。真发生时面板会标出来 |
| **额度池是共享的。** Codex、ChatGPT Work、ChatGPT for Excel 吃同一个池子，但这个接口只看得到 Codex | **花费偏低，推算额度跟着偏低** |
| **已用百分比精度粗** —— 接口只给到整数位 | 已用 1% 时推出来的额度没有意义；超过 50% 才值得信 |

有两件事接口根本不提供：

- **单次 turn 的花费。** 最细只到「天 × 模型 × 速度」。面板给的是「单 turn 最贵的**那一天**」
  和「单 turn 最贵的**那个模型**」。
- **按仓库 / 按项目的花费。** `code-attribution` 只接受 `group=workspace`，其他分组一律拒绝。
  能拿到的最接近的维度是**入口** —— CLI、VS Code、网页、GitHub、Slack。

## 统计范围

所有请求都带 `workspace_user=true`，所以数字只覆盖**当前 seat**。
不带这个参数的话，`daily-workspace-usage-counts` 返回的是整个 workspace，
而已用百分比是你个人的 —— 分子和分母根本不是一回事。

## 开发

`smoketest.html` 把录下来的真实接口响应喂给脚本，不联网、不用登录：

```bash
python3 -m http.server 8731
```

| 地址 | 场景 | 预期 |
|---|---|---|
| `smoketest.html` | 一天真实数据，30.4 天窗口，已用 99.93% | **花费 $249.83 / 额度 $250.00** |
| `smoketest.html#multi` | 7 天窗口，一个跑完的周期，24 天后续费 | 周期分段、速度基准、多份额度推算 |
| `smoketest.html#fresh` | 周期刚重置，已用 0% | 自动落到订阅视图 |
| `smoketest.html#hourly` | 5 小时窗口 | 拒绝推算额度，并说明原因 |
| `smoketest.html#fast` | fast mode，含一个没公布倍率的模型 | 2.5× 生效，另一个被标注 |

第一条是真正要守住的回归测试：那天是真实用量，$250.00 是它应该复现出来的额度。

测试桩**故意**按 `start_date` / `end_date` 过滤。不过滤的话，一个场景可能会用真实脚本
根本取不到的数据"通过"测试 —— 取数不足的 bug 就是这么藏住的。
